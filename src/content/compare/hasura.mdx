Hasura and Apso both save you from hand-writing API boilerplate, but they start from opposite ends. Hasura DDN puts a governed GraphQL API over databases and services you already run, and federates them into one supergraph. Apso starts from a schema your agent writes and generates the backend service: the database tables, the REST API, the access guards and the migrations, as code in your repository.

So the first question is simple. Do you have data sources to unify, or do you have a product to build?

<ShortAnswer>
  <Choice title="Choose Hasura when">You already have databases and services, GraphQL is the contract your clients want, and you need one governed API across several data sources.</Choice>
  <Choice title="Choose Apso when" highlight>You are building a new product or a new service, an agent is doing much of the work, and you want each change to produce the same kind of backend code your team can read and extend.</Choice>
</ShortAnswer>

## What each change costs

Hasura's permission model is a real strength. Permissions are declared per role in metadata, and Hasura defaults to safe: "whenever a new model is created in your supergraph, all records are only accessible to the `admin` role." A forgotten rule fails closed.

Failing closed is safe, but it still means every new model needs its own work before the feature can ship: a model permission with the right row filter for each role, type permissions for the fields each role may see, and command permissions for mutations. That configuration lives in Hasura metadata, separate from the table it protects and from the logic in your connectors. The table, the API and the rules are three places to keep in step on every change.

## One change, both ways: add team invitations

**On Hasura**, the change touches three layers:

1. Create the `invitations` table in your database with a migration you write.
2. Add it to the supergraph as a model, then write model, type and command permissions for each role, with a filter that checks workspace membership.
3. Put the email-sending and accept logic in a lambda connector, in TypeScript, Python or Go.

Then build and deploy the supergraph.

**On Apso**, the agent adds one entity to `.apsorc`, the schema file in your repository:

```json
{
  "name": "Invitation",
  "scopeBy": "workspaceId",
  "created_at": true,
  "fields": [
    { "name": "email", "type": "text", "is_email": true },
    { "name": "role", "type": "enum", "values": ["Admin", "Member"] }
  ]
}
```

`apso generate` writes the entity, the REST endpoints and a guard that filters lists to the caller's workspace, sets `workspaceId` on create, and checks ownership on reads, updates and deletes by id. The table, the API and the access rule come from the same ten lines, so they cannot drift apart. The email logic goes in `src/extensions/`, which generation never overwrites.

**The limits.** The guard runs on the generated API endpoints, not inside the database, so code in `extensions/` that queries the database directly is not filtered by it. Generated scoping ships in the TypeScript generator today, not yet in Python or Go. Apso generates REST, not GraphQL.

## Side by side

| | Apso | Hasura |
| --- | --- | --- |
| What it is | A generator that writes your backend service | A federated GraphQL API platform (DDN) |
| Starting point | A schema your agent writes | Databases and services you already run |
| API | Generated REST endpoints | GraphQL across connected sources |
| Where access rules live | `scopeBy` in the schema, generated into guard code (TypeScript today) | Per-role permissions in supergraph metadata |
| A new table or model with no rule | Gets the generated guard if it declares `scopeBy` | Admin-only until permissions are written |
| Business logic | TypeScript, Python or Go in `extensions/` | Lambda connectors in TypeScript, Python or Go |
| Who owns the database | You do; Apso defines the tables from the schema | You do; Hasura connects to it |
| License | Generator, templates and generated code are Apache-2.0 | v2 engine and connectors are Apache-2.0 |

## Where Hasura is the better choice

- **You have several data sources.** Federating Postgres, other databases and services behind one API is what Hasura is built for.
- **GraphQL is the contract.** If your clients want GraphQL, Hasura gives it to you. Apso does not.
- **You want declarative, deny-by-default permissions.** Hasura's role model is mature and fails closed.
- **The database already exists.** Hasura adds an API without changing who owns the schema.

## What you keep if you leave

**Leaving Hasura**, your data never moved, because Hasura connects to your own databases. What you rebuild is the API layer: the permission metadata, the GraphQL contract your clients use, and the wiring around your connectors. Running Hasura's data plane on your own infrastructure (Private DDN) requires an Enterprise agreement.

**Leaving Apso**, the backend is standard NestJS, FastAPI or Gin code in your repository with no Apso runtime, and it runs with Docker or the framework's tooling. You give up Apso's infrastructure automation: provisioning and hosting with managed Postgres, environment management, dashboard logs and data views, and `apso deploy`. Exporting gives you the application code. The infrastructure automation is the part you pay for.

</KeepBand>

## Bottom line

Hasura is the better tool for putting one governed GraphQL API over data you already have. Apso is for building the service itself, where every new entity gets its table, its API and its access rule from one schema change, and the tenth change looks like the first.
