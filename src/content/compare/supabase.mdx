The first version of an AI-built app is the easy part. You describe it, the agent builds it, and Supabase gives it a database, auth and an API in an afternoon. The hard part comes with the second feature, and the tenth. Each change is generated fresh, and nothing makes the new table follow the rules the last one did.

That is the real decision between Supabase and Apso. Supabase is a hosted Postgres platform where you configure the backend. Apso is a generator: your agent describes the change in a schema file, and Apso writes the backend code the same way every time, into your repository.

<ShortAnswer>
  <Choice title="Choose Supabase when">The database is your backend, you want realtime subscriptions out of the box, and you are comfortable writing and reviewing a Postgres policy for every table you add.</Choice>
  <Choice title="Choose Apso when" highlight>Your app already has users and keeps changing, when an agent is making most of those changes, or when you need the backend to be code your team owns and reviews like the rest of the product.</Choice>
</ShortAnswer>

## Where the second feature goes wrong on Supabase

On Supabase, access control is a Row Level Security policy written on each table. It is real database-level enforcement, and when it is in place it applies to every query. The catch is that it has to be in place on every table, every time.

Supabase's own docs describe the default. Tables created in the dashboard have RLS turned on. Tables created in the SQL editor "or through another tool," which includes most agent-written migrations, need it turned on explicitly. Without it, "a table in an exposed schema without RLS is readable and writable by any role with a grant on it." On existing projects, new tables in the `public` schema get those grants automatically. Supabase has said it is changing that default and has added a setting to stop new tables being exposed. Check yours.

This is the failure that shows up in practice. VibeEval's [Supabase RLS Misconfiguration Atlas](https://vibe-eval.com/data-studies/supabase-rls-misconfiguration-atlas-2026/) (November 2025 to April 2026) ranks RLS switched off as the most common failure, ahead of permissive policies and partial coverage. Its explanation for AI app builders is structural: "the platform's generator adds tables incrementally as features are added," and "the policy-creation step does not always run on the new table." The atlas publishes a ranking, not a prevalence rate, so treat it as a list of what goes wrong, not how often.

None of this is a flaw in Postgres or in Supabase. It is what happens when a rule has to be remembered by whoever writes each new table, and more of those tables are now written by a model.

## One change, both ways: add team invitations

Say your app has workspaces, projects and tasks, and the next feature is team invitations.

**On Supabase**, the agent writes a migration that creates an `invitations` table. Then someone has to:

1. Enable RLS on the new table, if it was created in SQL.
2. Write select, insert, update and delete policies that check workspace membership.
3. Test that a member of one workspace cannot read another workspace's invitations.
4. Write any server logic, such as sending the email, as an Edge Function.

Step 2 is the one that gets skipped. Nothing fails when it is missing. The feature works in the demo, and the table is open.

**On Apso**, the agent adds an entity to `.apsorc`, the schema file in your repository:

```json
{
  "name": "Invitation",
  "scopeBy": "workspaceId",
  "created_at": true,
  "fields": [
    { "name": "email", "type": "text", "is_email": true },
    { "name": "role", "type": "enum", "values": ["Admin", "Member"] }
  ]
}
```

Then `apso generate` writes the service code. Because the entity declares `scopeBy`, the generated guard does the same three things it does for every other scoped entity:

- `GET /Invitations` returns only the caller's workspace's rows.
- `POST /Invitations` sets `workspaceId` from the authenticated request, so nobody can create one in another workspace.
- Reads, updates and deletes by id check that the record belongs to the caller's workspace first.

The reviewer reads a ten-line schema change instead of a migration plus four policies, and the tenth entity gets the same guard as the first. Custom logic, like sending the email, goes in `src/extensions/`, which generation never overwrites.

**Be precise about the limits.** Apso's guard runs on the generated API endpoints. It is application-layer enforcement, not a database policy, so code you write in `extensions/` that queries the database directly is not filtered by it. Generated scoping ships in the TypeScript (NestJS) generator today. The Python and Go generators produce the service without it.

## Your agent's tools: change the database, or change the plan

Supabase has an official MCP server. Its tools include `execute_sql` and `apply_migration`, which run against your project. Supabase offers a read-only mode, single-project scoping and development branches to keep that safe, and those are worth using.

Apso's MCP server takes the other approach. Its tools design and validate the schema, generate code and diagnose problems. None of them write to a database. The agent proposes a schema change, the generator turns it into code, and the change reaches production through your normal pull request and deploy.

## Side by side

| | Apso | Supabase |
| --- | --- | --- |
| What it is | A generator that writes your backend service | A hosted Postgres platform |
| Where access rules live | `scopeBy` in the schema, generated into guard code (TypeScript today) | RLS policies written on each table |
| A new table with no rule | Gets the entity's generated guard if it declares `scopeBy` | Exposed on existing projects unless RLS is enabled |
| What the agent changes | The schema file, reviewed in a pull request | The live project, unless you use read-only mode or a branch |
| API | Generated REST endpoints | Auto-generated REST and GraphQL over Postgres |
| Business logic | TypeScript, Python or Go in `extensions/` | SQL functions, triggers and Edge Functions |
| Auth | BetterAuth, Auth0, Clerk, Cognito, API keys or custom sessions | Supabase Auth |
| Realtime | Not generated | Broadcast, Presence and Postgres Changes |
| License | Generator, templates and generated code are Apache-2.0 | Platform is Apache-2.0 |

## Where Supabase is the better choice

- **Realtime is the product.** Presence, broadcast and change subscriptions are built in. Apso does not generate them.
- **You are on version one.** If the schema is small and you will review every policy yourself, Supabase gets you to a working app faster.
- **You want enforcement inside the database.** RLS applies to every query, including SQL you write by hand. Apso's guard covers the generated API.
- **You want auth, storage and functions in one bill.** Supabase bundles them. With Apso you choose an auth provider and run the service.

## What you keep if you leave

**Leaving Supabase**, `supabase db dump` exports your roles, schema and data. Storage files move separately. You rebuild auth, every RLS policy, your Edge Functions and the client calls that depend on the Supabase SDK. You can self-host Supabase with Docker, without branching, managed backups or point-in-time recovery.

**Leaving Apso**, the backend is already standard NestJS, FastAPI or Gin code in your repository, with no Apso runtime. It runs with Docker or the framework's own tooling. What you give up is Apso's infrastructure automation: provisioning and hosting with managed Postgres, environment management, the logs and data views in the dashboard, and `apso deploy`. Exporting gives you the application code. The infrastructure automation is the part you pay for.

</KeepBand>

## Bottom line

Supabase is a strong platform for getting the first version of a Postgres app live. It asks you to get the access rules right on every new table, and agents add tables quickly. Apso is for the stage after that: the agent describes each change in one schema file, and the generated backend follows the same pattern on the tenth change as it did on the first.
